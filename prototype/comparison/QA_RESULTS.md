# 运行对照记录

## 2026-09-24 用户评审后的纠偏

用户认为 A 的光影与真实感优于 B，C 表现一般。B 的旧称“改良”不是质量结论；当前改称“3D 试验”。D 复用了 C 的绘制代码并降低内部渲染分辨率，**不能作为真正像素美术路线的评估样本**，也不能用它否定像素路线。旧 PNG、视频、日志与运行代码保留，画面内旧标签属于历史记录。

新增角色、房间和 UI 实现已暂停，须先与用户讨论。见 [本轮研究](ROUND2_RESEARCH.md)：A/B 的光照、投影和几何差异是源码支持的机制线索，尚未通过单因素实验确认各因素贡献；许可候选均未下载或采用。原参考视频的屏幕提示词仍待主协调任务直接核验，本轮不把旧观看摘要或 ASR 当成新证据。

日期：2026-09-24。范围：#20 的路线评审原型；**尚未选择首版画风，也不是桌面伴随产品验收通过**。

## 可复现范围

- 原 3D 对照 A、改良 3D B、原创等距 2D C、像素化研究 D，共用 `tasks.json` 三项虚构任务及同一 `comparison.gd` UI。房间和角色保持同一语义、配色身份，但构图与角色占屏并非逐像素一致，不能把本轮当作仅改变渲染器的实验。
- 三种逻辑客户区：1280×720、800×600、360×320；两种光照。默认小窗是右上角 360×320。
- Apple M5、macOS、Godot `4.7.stable.official.5b4e0cb0f`，OpenGL 4.1 Metal Compatibility。普通场景 4× MSAA；统一 30 fps 上限。没有启动编辑器做采样。
- 本机 Retina 缩放为 2：对应窗口/PNG 2560×1440、1600×1200、720×640。JSON 同时记录 `viewport`（逻辑）、`window_pixels` 和 `display_scale`。网页按逻辑宽度展示，原图保留两倍像素。**最初按物理像素设置的旧批次已全部替换，不能用于实际小窗可读性结论。**

## 桌面层级、透明与遮挡

默认小窗设置置顶，完整应用可切普通窗；收起为无边框小房子。半透开关设置的是窗口/背景透明能力，不让任务文字一起变淡。用的是 Godot 官方 [Window API](https://docs.godotengine.org/en/4.6/classes/class_window.html)；高分屏像素口径依据 [DisplayServer API](https://docs.godotengine.org/en/4.6/classes/class_displayserver.html)。

实际检查包含原生窗口收起、恢复、展开、任务状态保留、半透开关，以及 `desktop-test.html` 的条纹背景/点击计数控制样本。控制页正常点击计数增加；通过窗口绑定工具点击小房子透明边缘后未观察到控制页计数增加。窗口截图工具只输出目标窗口，没有桌面合成，因此**透明合成、跨应用穿透、真实遮挡层级均未记为通过**。这个结果尚不能区分操作系统行为与工具输入路由限制。

以下仍待专门桌面验收：Codex/浏览器普通切换下的持续置顶与焦点、不遮常用按钮、桌面背景层、闲置自动变淡、全屏应用、Mission Control、双显示器、跨显示器 DPI 变化。当前不是安装包，没有系统启动项或驻留服务。完整应用展示的是同一原型清单，不等于已接入完整业务工作台。

## 性能采样

采样完成，四模式各60个原始样本。原始 `performance.json` 保留每秒的 `ps` CPU/RSS；单一 Godot 进程逐模式运行，预热30秒、采样60秒，同为逻辑360×320、Retina720×640、白天、30 fps。CPU 100% 表示约一个核心，不是整机100%。正常桌面其他应用未关闭，因此结果是这台机器这轮运行的观测值。

| 模式 | CPU中位数 / 峰值（单核%） | RSS中位数 / 峰值（MiB） | 引擎采样fps |
| --- | ---: | ---: | ---: |
| A 原3D | 11.2 / 14.3 | 312.0 / 312.0 | 30 |
| B 改良3D | 11.3 / 14.5 | 191.6 / 191.7 | 30 |
| C 等距2D | 24.9 / 26.9 | 195.6 / 296.7 | 30 |
| D 像素化2D | 24.8 / 27.1 | 305.4 / 306.2 | 30 |

单轮结果中C/D的CPU读数更高，并不能推出2D路线本身更贵；当前2D每帧重新提交绘制的实现是待隔离验证的因素。RSS也受驱动/分配时机影响，本轮没有重复试验，不能据此对路线做稳定内存排名。

`*-idle-frames.json` 是最近1800次 `_process(delta)` 间隔汇总，含帧率上限等待；它不是 GPU 单帧渲染耗时或输入延迟。冷启动到可操作没有独立时间探针，矩阵 wall time 包含截图/流程，不能拿来宣称冷启动达标。活动时CPU/RSS、连续10分钟运行、耗电量仍未测。

## 剩余视觉与实现限制

- C 的小窗角色约35–40逻辑像素高，B更大；橙色衣服和位置清楚，五官/背包/手势仍弱。两者角色占屏不同，不能据此断言2D或3D天然更可读。
- B是基础几何、刚体关节动画的改良候选；没有成熟人物网格、骨骼权重或专业角色动作。白天材质偏亮、夜晚场景与浅色任务UI的融合仍可打磨。
- C是固定视角绘制，暂无完整背/侧面角色资产；D只是同图低分辨率最近邻版本，细节丢失更多，也不是手工精修像素美术。
- 任务状态保存在当前进程，重新启动恢复虚构fixture。演示完成不等于投递、考试通过或技能掌握。没有自动规划/重排计划。
- 素材均由原创程序几何/绘制生成，现有原创灯具来自提交的Blender脚本；没有下载第三方资产、复制游戏素材或付费调用。来源详见 `ASSET_LICENSES.md`。

## 发布前检查与结论边界

隐私脚本仍将 `prototype/` 标成 `not_in_share_allowlist`，本轮没有扩大白名单或把这个结果写成自动通过。人工复查提交范围：只有虚构任务、原创源、应用自身PNG/MP4、脱敏日志与说明；没有保存桌面/浏览器截图，未纳入 `.godot` 缓存、字体副本、凭证或私人数据库。GitHub目标归属与认证账号另在推送前核对。

本轮运用 decision-check：P1 修正了高分屏尺寸与自动点击坐标，并把桌面截图/输入工具限制从产品结论中分离；P2 不沿用“3D一定贵/2D一定好看”之类旧归因；P3 使用独立审图、真实输入及原始资源采样反查自动 proof。证据支持“可运行并可比较的候选”，不支持“最终美术质量或所有桌面集成门槛已过”。先由用户在实际小窗和完整应用间比较 B/C，再确定首版路线及修订范围。
