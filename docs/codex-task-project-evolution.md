# 方法与产品的演进记录

本文件只记录可以分享的通用问题和决策，不保存真实个人事项、私人原话或任务数据库。首版日期：2026-09-29。

## V0：把计划与实际行动分开

讨论形成的方向是：明确目标 → 安排一次小行动 → 留下活动与产物 → 核对结果 → 解释偏差 → 选择下一步。核心约束是活动、AI 产物和本人结果不能互相替代。相关产品设计见 [PR #14](https://github.com/johnnyzhang-eng/career-workbench/pull/14)，其讨论与草稿不代表最终实现。

## V1：从画计划转向收集真实事项

问题：只有计划图，仍然不知道今天从哪里开始。

修正：先读取用户明确指定的资料，把急事、长期方向、未知日期和真实时间预算整理出来。收集允许继续补充，先选择一个小行动，不急于生成完整日历。

## V2：从混在总聊转向独立任务对话

问题：不同方向混在一个对话里，用户难以在侧边栏找到入口，下一步也容易串线。

修正：总览处理优先级与冲突；每个持续方向有稳定编号、独立对话和交接。Project 按共同资料和目标组织，侧边栏分组帮助识别。建好入口后等待用户推进，避免长期方向一起自动开跑。

## V3：从多个副本转向共享清单

问题：每个对话自行保存完整清单会制造过期记录和写入覆盖。

修正：只指定一个事实来源；更新只涉及本任务。最小版本可以人工回传 Markdown；需要多个写入方时使用版本检查、事务和历史。

本地原型已经实现任务注册、显式更新、版本冲突检测与定期读取展示，验证了进展能保存并恢复。这不代表读取了所有任务对话，也不代表持续监测已启动。该代码尚未随本次文档 PR 交付；可运行方式应等对应代码集成说明。

## V4：把清单接回小屋子

问题：先把清单放在一张普通网页，偏离了既有小屋子入口。

修正：房间保留，小窗呈现当前行动，展开面板呈现完整任务清单。清单功能和用户熟悉的产品入口需要一起验收。相关原生小屋子集成仍在 [PR #62](https://github.com/johnnyzhang-eng/career-workbench/pull/62) 等草稿切片中。

当前证据：本地浏览器和实际原生浮窗中均检查了房间、当前行动及完整清单；原生窗口实际执行了展开、收起和从房子入口恢复。保存结果能写入共享记录。对话跳转、退出重开和长期常驻仍需单独验收，不能用这些局部检查替代。

## V5：把实践整理成同学能复制的材料

本次交付：方法指南、提示词、虚构示例和本演进记录；根目录提供入口。公开仓库只承载通用材料，每位同学的事实和进展独立保存在本机。

接下来要验证：同学能否不用解释就找到下一步；不同对话的回传是否准确；小屋子能否减少入口切换；工具是否实际帮助产生本人结果。没有试用数据时，保留问题，不写成已证实的效果。

## V6：侧边栏保留任务入口，当前状态不累积整段历史

问题：长期对话的过程越来越多，当前摘要若不断追加，也会变成另一份长历史。仅清空聊天会丢掉约束和接续依据。

修正：总清单、短当前交接和历史产物分层保存。侧边栏保留稳定编号和当前任务入口；阶段交接后再决定是否换对话。已有数据库版本历史继续保存，当前摘要改为最新结果与下一步。任务有结果时回传，总览读短记录，需要时才核对对应回合。

本次材料增加入门页、空交接模板、保存与恢复提示词，以及按变化查看进度的设计。文档链接、隐私预检与仓库既有虚构演示可检查；自动增量检查器未交付，token 节省和长期效率改善尚无测量结论。一次本地有界核对发现任务清单落后于已有结果：负责人核对指定文件后修正短交接和自己的记录，存储中旧、新版本均保留。本轮未执行任务之外的修改。这个检查覆盖记录纠偏，不是新用户盲测，也不是自动监测或节省 token 的证据。后续仍应检验全新对话能否仅凭交接正确续接。

## V7：main 可直接使用，首次访谈填自己的事项

问题：仅提供草稿分支链接，需要使用者辨认版本；只给空任务卡又容易遗漏真实承诺、等待项和生活事务。

修正：将经核验的产品协作基线 #7 和方法文档 #75 合入 main。增加渐进访谈、领域查漏、期限来源与现实约束、本人校正、空清单和首次行动；在入门页给自己的 Codex 提供 main 启动与更新消息。仓库 AGENTS 仅在用户要求任务组织时引导访谈，不干扰普通开发请求。

仍待验证：不同使用者是否能独立完成首次访谈、第一次回传与后续接续。任务进度自动增量检查、小屋子完整发布和 token 效果仍按[交付状态](method-delivery-status.md)记录。合并文档不代表这些软件功能完成。

## V8：同学版只用 Codex，自动续接留待后续

收紧试用范围：同学只使用侧边栏、总览、独立任务对话和本地清单；小屋子由作者继续试验，不作为同学安装或启动要求。入门页增加可直接转发的消息。

自动历史压缩与建立新阶段对话分开说明；任务收尾依据验收结果，回合完成不能代替任务完成。当前不启用自动建聊、归档或额外监测，先检验手动交接与回传。

## V9：在实际使用中观察，自动操作仍需验收

增加标准库本地检查器，只增量读取明确登记的对话日志。累计 token 不用于压力判断；最近一次输入比率仅是试验提示，压缩后作废旧样本。回合结束与任务完成分开。元数据、游标和真实配置留各人的 `private/`，没有模型或网络调用。

真实本机试验发现截图与压缩记录可超过最初读取上限；修正读取上限并增加大记录验证，避免把适配器的测量问题算成任务停滞。增量观察与低频模型复核分开启用，后者会消耗模型用量；无变化不反复读全部聊天，总览忽略自己的复核回合以免形成自触发循环。脚本持续运行与用量、长期效果及独立续接效果分开验收。[试验方法与启停说明](codex-thread-watch.md)。

尚未实现自动创建阶段对话、自动切换入口或归档。不同客户端版本的本地格式兼容性仍需验证，不属于同学首次启动要求。

## V10：建议标题不等于侧边栏已经改变

一次同学试用反馈揭示两个可复用的卡点：当前会话没有线程命名或侧边栏管理工具时，助手能提出标题，却无法证明客户端已改变；任务编号只在该使用者自己的清单里有意义，不应套用作者或示例的 T02。反馈属于入口核对问题，不意味着必须让同学安装小屋子。

启动消息、访谈、提示词和空清单改为逐项记录建聊、改标题、移动分组的能力与核验状态。缺工具就给可复制内容，由本人手动完成；结果与下一步从任务对话显式回传到同一清单或总览。公开材料只描述通用触发和修正，不收录同学聊天或私人任务内容。

入门页另附一段已开始试用时可直接发送的补救消息：明确授权改现有标题和分组，读回验证；无工具时转为本人手动操作，不重做任务访谈或另建重复对话。

待验收：同学能否实际完成手动改名、回报当前标题，并在一次真实行动后顺利把结果带回总览。文档修正与作者侧工具可用，不代替同学端实际成功。

已有 `private/tasks.md` 无需重编号或自动改名；更新模板时保留原有入口与历史，无法核实标题就加注“待核对”，等本人或工具读回后再标已验证。

## V11：引用工具与任务入口都要按本次证据核对

另一段试用回放中，使用者选择了投递作为当前重点并引用了两个旧对话。总览一度因本次没有读取工具要求使用者复制旧进展；后续回复称已从本机记录核对，并在总览给出岗位候选表，最后才承认应回到任务入口。回放没有提供足够证据复核每个岗位来源和开放状态，本轮不判断岗位本身的真伪。旧对话能否承接整个新方向不能仅凭关联标题判断。

修正：对话读取先试本次可用的线程工具；若目标不可读，再检查授权范围内是否有精确 ID 的本机记录，两者都没有就保留未知并只要短交接。按目标、资料、产物、阶段与验收来决定复用旧对话；总览只做安排、必要的有界准备和结果回传，选定重点后把具体执行放到核实过的任务入口。没有跨对话工具时给使用者可粘贴消息，不把清单里的路由写成已送达。

当前只拿到使用者提供的总览回放；引用的两个旧对话在作者当前环境无法读取，因此不对它们的真实内容或应否复用下结论。试用后续仍需核对：任务入口是否适配、是否真正进入对应对话完成一次动作、结果是否回到总览，以及标题是否实际改变。

## V12：急事先行后仍要发现长线与阅读

问题：首次访谈虽然有“阅读、兴趣”和“长期项目”的查漏表，但实际试用容易在确定眼前重点后就停止追问。这样清单只覆盖紧急交付，使用者想随时点回去的书籍、学习主题和长期作品不会形成入口。

修正：保留急事先行和每轮 1–3 问，同时明确下一轮轻问想读的书、长期项目、想学主题与兴趣。分别记录“当前推进”“有入口但暂不推进”“只留清单候选”；无硬期限的长期方向也可有稳定对话，但由使用者选择，不能自动制造空入口或把所有方向同时开跑。

待验收：下一位首次使用者能否在处理急事后补出真实长线方向，并准确决定它是侧边栏入口还是候选；没有长线方向的回答同样有效，不追求入口数量。

## V13：已确认的入口不等待整张清单定型

问题：一次后续试用中，总览已保留若干稳定编号，却继续询问新增长线方向是否需要入口、已有学习方向是否拆分。新增方向的选择可以继续讨论，但不能让已经确认并获建聊授权的入口一直停在“待落实”。这段回放没有证明该客户端当时有管理工具，也没有证明侧边栏已改变。

修正：把入口落实改为增量步骤。每校正且授权一批方向，先核对并落实该批；其余候选继续留清单。宽泛学习方向可先用一个总入口，拆分以后再决定。工具可用时执行并读回；工具缺失时同轮交付每个入口的准确标题、首条交接与本人手动操作，不把“待落实”当作已完成或下一轮再处理的理由。

待验收：试用者能否先完成已确认入口的改名或新建，随后再决定阅读、兴趣等候选方向；必须以实际客户端标题或本人操作确认作为证据。

## V14：创建返回值与侧边栏搜索分开核对

问题：一段后续试用回放中，助手在侧边栏管理工具不足时转去探索本地 app-server 接口。它报告改名成功，但新建空对话未出现在搜索结果后，又发起一次创建并准备归档、重建。回放不足以判断搜索为何缺失，也不能据此判断哪一个入口实际可见；已经返回的创建 ID 才是继续核对的起点。

修正：首次任务整理只检查当前提供的工具，缺失就交付手动操作，不把内部接口探测变成入门流程。每次创建保存返回的 ID 或异步标识；搜索缺席只标可见性待核验，不触发再次创建。若已产生重复，冻结新建和归档，核对各 ID、运行状态、实际消息和本人可见入口，再决定如何收敛；不凭标题或搜索结果自动清理。

待验收：在客户端新建一个入口后，能用同一 ID 完成首条交接并确认侧边栏可见；若搜索暂不可见，流程仍不会生成第二个同名入口。真实试用结果与离线文档检查分别记录。

## V15：先有一次真实推进，再补齐侧边栏

问题：试用截图显示已出现总览和任务标题，任务入口里却只有交接消息；总览仍在核对 ID 和解释入口。截图不能说明底层创建或搜索为何异常，也不能证明其他位置没有做过任务工作，但足以提示首次引导把入口完整性放得过重。仓库旧入门页有多段相似启动提示，把访谈、建聊、分组、核验和更新同时交给新用户，容易让环境整理占据第一次使用。

修正：入门页缩成“已有入口直接做事”和“新用户先做一个入口”两条路径，要求第一次留下可核对的任务结果与下一步。接口或侧边栏能力只做一次有界检查，缺失即给手动步骤并回到任务；详细恢复步骤移到参考页。长线项目、阅读等继续在后续轮次渐进询问，保留用户决定哪些留左侧的权利，不要求首次排满。

待验收：新使用者在已有入口时能否停止重整侧边栏，直接完成一个实际动作并回传总览；新用户能否在不探测内部接口的情况下获得一个可用入口。文档更新本身不是试用通过。

## 后续记录格式

每次发生影响方法或体验的修改，追加一项：问题与触发条件、具体修改、实际检查、剩余限制、公开代码或文档链接。修正旧结论时同步更正原位置，保留更正说明。私人证据可以留在本机，公开只描述可分享的验证方法和范围。
