# 对话变长以后，怎样继续推进

侧边栏是任务入口：稳定的编号和名字，让人点进去就知道要做什么。聊天记录可以很长，但接续任务所需的信息应当很短。本文件是协作协议；不会自动启动对话监测。

## 三层记录，各有用途

| 记录 | 保存什么 | 什么时候读取 |
| --- | --- | --- |
| 总清单 | 每项任务的状态、当前对话入口、下一步、更新时间、依据位置 | 总览或小屋子展示任务时 |
| 当前交接 `T01-current.md` | 当前阶段目标、最新结果、卡点、一个下一步、约束和资料索引 | 本任务继续或换对话时 |
| 历史与产物 | 阶段记录、尝试、题目、代码、验证结果及旧版本 | 核对具体事实或寻找遗漏时 |

总清单和交接文件描述同一个当前状态，不能各自成为独立事实来源。写清总清单位置与版本；文件过期时先读总清单，再核对相关依据。多个对话只更新各自任务，版本冲突时合并，不覆盖其他人的改动。

历史先保存，再替换当前摘要。数据库已有版本历史时使用它；只有 Markdown 时，先把上一个阶段的记录保存到 `private/history/`，确认成功后再更新当前文件。禁止靠删掉旧结果换取简短。

## 当前交接保持一屏可读

推荐正文约 300–600 个中文字，作为人工编辑目标，不是硬截断上限。重要约束宁可保留完整，也不要为了字数删除。用[空模板](context-templates/task-checkpoint.md)记录：

1. 哪个任务、哪个阶段、谁负责、更新时间和来源版本。
2. 已发生的最新结果及依据，区分独立完成、带提示完成和 AI 产物。
3. 尚未解决的问题与必须保留的约束。
4. 下一次只做哪一个动作，留下什么，怎样验收。
5. 需要时才读的资料路径与历史索引。

不把所有旧进展继续追加进“当前进展”。总览只保留优先级、时间冲突、待决事项和入口，不重复八个任务的完整过程。新事实出现后才更新；进入对话、打开文件或时间过去，不足以判定进展。

## 什么时候换对话

先在原对话继续，按自然阶段保存交接。出现以下情况时，再建议换到新的阶段对话：

- 开始一个目标或资料明显不同的新阶段。
- 已多次混用旧计划、忘记当前约束，短交接仍未解决。
- 用户希望一个更清爽的工作入口。

换之前保存交接与产物；用户明确要求创建时才新建。沿用任务编号，例如 `T01 数据库｜连接查询`，交接中写旧对话入口。先在新对话核对目标、已完成、未知和下一步，再推进；核对通过后将总清单入口改为新对话，旧对话保留在历史分组。用户仍需接续的工作不要提前归档。侧边栏只保留各任务的当前入口，避免堆出一串同名“续聊”。

Fork 会带上旧历史，不能把它当作只有短交接的新起点。官方 CLI 提供 `/compact` 压缩上下文；本协议不依赖桌面客户端是否提供相同入口。[官方命令说明](https://learn.chatgpt.com/docs/developer-commands?surface=cli)

## 怎样查看每个对话的进度，减少重复读取

默认采用“有结果就回传”：任务对话完成一次实际行动后更新自己的短记录，总览读取清单，细节按需核对。刷新本地清单无需模型推理；定期调用模型重读每个完整对话会增加重复输入。

如果以后启用检查器，建议记录每个任务上次处理的版本或游标，只处理新增结果。已有回传无需再重复推断；没变化就保持安静。发现“对话报告已完成、清单仍待推进”时，标记待核对，读取对应回合及依据，不能仅凭一句完成宣告覆盖记录。错误与超时标成未知，不能当作进度为零。保留负责人和手动更正入口。

| 信号 | 可以登记 | 不能直接推断 |
| --- | --- | --- |
| 本人作答、运行结果、实际回执 | 对应动作及已核验范围 | 整个长期目标完成 |
| 对话中的计划或 AI 解答 | 待执行建议或候选产物 | 本人已经完成或掌握 |
| 一段时间没有更新 | 最后更新时间、需要时询问 | 懒惰、放弃或失败 |

定时检查、跨对话协调与活动监听需要另行明确数据范围、频率、触发条件和授权。没有启用时展示“手动回传”；不要称为已自动监测。输入量、模型、工具调用和频率都会影响 token 与费用，没有测量时不报节省比例。

## 验收一次续接

仅根据当前交接和明确引用的必要资料，能否回答“在做什么、已做什么、还不知道什么、下一步是什么、哪些动作需用户决定”？再与最新清单核对。如果依赖翻遍旧聊天才能回答，补交接；如果交接与依据冲突，先修事实，不盲目执行。一次接续成功说明该次交接可用，不证明长期效率提高。
