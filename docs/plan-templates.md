# 秋招与 CET6 首版计划模板（#27 草案）

状态：规则模板适配器，依赖 [#24 的通用目标契约](https://github.com/johnnyzhang-eng/career-workbench/pull/24)。只产出**待本人接受、编辑或拒绝的提案**，不写入生效计划，不运行任何每日任务，也不调用模型或外部服务。所有测试和演示人物、岗位、练习数字均为虚构。

## 输入与输出

`build_first_plan(goal, path, start_on, proposal_id, job=None, official_sources=None)` 接受已存入 `GoalStore` 的目标快照、目标本地首日、提案 ID，以及可选的本地岗位引用。`path` 明确为 `recruiting` 或 `cet6`；其他领域请本人手动建任务。返回值包含：

- `proposal`：符合 `GoalStore.propose_plan` 的完整七日提案。`method=rule_template`，`base_version=0`，每项均有预计分钟、理由、完成规则、来源与假设引用。
- `unknowns`：不能可靠推断的考试日期、报名、岗位截止、岗位来源或时间冲突。摘要也写入提案 `reason`，接受后仍能看到；截止字段保持 `unknown/null`，除非确有带来源和核验时间的外部截止。
- `budget`：用户填的七日可用分钟、建议投入与未分配分钟。模板每天至少需要 15 分钟；少于 105 分钟会报告容量不足，交由本人修改目标或另拟更短计划，不压缩成无法完成的七天。
- `explanations`：供提案 UI 展示的逐项镜像。其理由和来源**同时写在各计划项中**，即使 UI 不保存 sidecar，接受计划后也不丢失。

每天 20:00 是**待本人编辑的默认时段**，不是读取了课表或日历。若七日末任务晚于本人设定的目标日，模板会要求重选首日或本人手动改拟计划。模板不会自动将本人设的目标日当官方考试日，也不会根据“招满即止”编造岗位截止；当前版本不依据具体可用时段排日程。岗位截止输入必须显式含 `deadline_confidence="verified"`、具体来源和带时区的核验时间，否则不能进入硬截止字段。此标记仍需上游人工核对真实来源，模板不能自行证实网页内容。

```mermaid
flowchart LR
  A[已存的 Goal 快照] --> B[容量与来源校验]
  B --> C[七日首版提案 + 逐项理由/来源]
  C --> D{本人决策}
  D -- 接受或编辑 --> E[GoalStore 生效版本]
  D -- 拒绝 --> F[保留未采用提案]
  E --> G[每日任务适配属于 #17]
```

## 两条模板的事实边界

秋招模板的行为顺序是工作流建议，引用本仓库 [`docs/workflow.md`](workflow.md) 的资格核验、材料版本确认和外部真实回执门槛。有具体本地岗位 ID 且无时间冲突时，D1、D4、D5 和 D6 可以给出岗位关联任务，但模板本身不检查岗位是否可投。D6 的完成规则只允许本人在**实际原站提交并核对回执之后**记录 `submitted`；打开页面、准备材料或点击跳转都不算提交。没有岗位 ID 时只安排发现、核验与准备，不生成虚构的岗位申请。已核验截止若早于模板默认投递时段，D1 提醒本人核对并重排，后续只保留通用材料任务，不安排过期投递或冒充针对该岗位的材料批准。

CET6 模板依据教育部教育考试院当前可访问的 [CET6 笔试结构](https://cet.neea.edu.cn/html1/report/16123/201-1.htm)安排听力、阅读、写作与翻译四类短练（官方页面发布于 2016-12-08，本次访问核对：2026-09-24）。该来源说明考试结构，**不证明模板的练习方法或用户能力**。考试院 [CET 笔试说明](https://cet.neea.edu.cn/html1/folder/16113/1586-1.htm)写明笔试通常在 6 月和 12 月，具体日期另行通知（本次访问核对：2026-09-24）；模板因此不生成某次考试日期。未提供当次公告、学校报名资格及个人确认时，报名均标记待核对。缺少已核对的官方结构来源时，D1 变成核对来源，其余任务只称普通英语短练，不声称当前 CET6 题型。模板不含真题或受保护题目。

每一次练习的完成规则要求保存**首次**作答、练习来源和错因。订正结果可另记，但不能覆盖首次成绩或自动判定掌握；阶段练习分数也不是正式考试成绩。D7 使用真实结果提出下周复盘，下一版仍需本人决策。

## 契约边界与下一步

此适配器不写 GoalStore，也不把计划同步到 DailyStore。调用方必须先展示逐项理由、预算、未知项和默认时段，再由本人触发 `propose_plan`，之后用 `decide_plan` 明确接受、编辑或拒绝。`GoalStore` 的项目字段需持久化 `reason` 与 `source_ref`；本 PR 与 #24 的对应契约变更一起评审。若要把来源核验时刻作为可查询独立字段，后续再扩数据契约；当前官方来源在 `source_ref` 中含访问日期，外部截止使用专门的 `due_checked_at`。

虚构离线演示：运行 `python3 -m unittest tests.test_plan_templates -v`。测试会创建临时 GoalStore，分别生成两条七日提案，确认提案不激活计划，再由虚构用户作一次接受/拒绝决策；它不会访问官网或发送任何对外请求。
