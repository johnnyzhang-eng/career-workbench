# 用 Codex 把零散事项变成能持续推进的任务

这份指南记录 Career Workbench 的一条实践路线：先把脑中和笔记里的事情说清楚，再为不同任务建立独立对话，用一份总览保留实际进展，最后把清单接到日常愿意打开的工作台里。方法仍在迭代；它没有证明使用者的执行力已经提高，也不保证学习或求职结果。

同学可以先用对话和本地 Markdown 清单跑通，不必等小屋子、数据库或自动化全部做好。配套材料：[可复制提示词](codex-task-project-prompts.md)、[虚构的一天](codex-task-project-example.md)、[演进记录](codex-task-project-evolution.md)。

## 先区分三种东西

| 名称 | 负责什么 | 什么时候拆出来 |
| --- | --- | --- |
| Project / 项目 | 一个有共同资料、产物和较长期目标的工作范围 | 要持续维护同一仓库或资料集时 |
| 对话 | 一条任务的上下文、讨论和接续入口 | 目标、资料或验收方式明显不同，继续混聊容易串线时 |
| 任务 | 有下一步和完成条件的一件事 | 能说出这次要交什么、如何判断完成时 |

一个项目可以有多个对话，一个对话可以连续完成多项小任务。侧边栏分组方便识别，但不会自动给这些对话共享记忆、文件或进展。这里的“总览”是一个普通对话，加上一份明确指定的本地任务清单，不意味着 Codex 自动掌握其他对话的一切。

若当前客户端没有创建 Project 的工具，就在客户端中创建，或先用侧边栏分组与独立对话。不要把分组称作已经建好的 Project。为每个实际工作范围指定资料目录；跨范围需要的内容写进交接文件，避免把整个私人目录当作共享上下文。

```text
00 总览：近期重点、任务清单、时间冲突
├─ 学习：T01 课程练习对话
├─ 求职：T02 岗位与面试对话
├─ 作品项目：T03 实现与验收对话
└─ 阅读：T04 理解与笔记对话
```

## 1. 先收集，暂不把每件事排满

把正在做、拖着没做、想做、担心忘记的事情都写出来。允许口语、重复和未知日期。指定 AI 可以读取的笔记或文件，先还原原意；补充不全时保留未知。

先确认三项实际约束：最早的确定期限、每天稳定能拿出的时间、今天必须发生的事情。想象中的最高强度不能当作每天都可兑现的预算。先安排一项能开始的行动，之后再补长线事项。

区分“已经确定的期限”和“估计时间”，也区分“我愿意推进”和“我已经安排了”。没有明确时间的想法可以留在待推进清单里。

## 2. 给任务稳定编号和可检验的下一步

建议从下面这些字段开始；它们是任务卡约定，不是 `career.py` 已支持的通用命令格式。

| 字段 | 内容 |
| --- | --- |
| ID / 标题 | 稳定编号 + 可识别的名字，例如 T01 数据库练习 |
| 目标 / 输入 | 想解决什么；可使用哪些资料；哪些关键事实未知 |
| 下一步 / 产物 | 下一次要做的具体动作，以及留下什么 |
| 验收 / 负责人 | 谁执行、谁核对；什么证据算完成 |
| 状态 | 待推进、进行中、卡住、暂缓、完成 |
| 时间 | 确定期限或明确标记的估计；预算和实际耗时分开 |
| 进展 / 依据 | 已发生的结果、证据位置、更新日期 |
| 对话入口 | 当前任务对话的标题或链接 |

“学好数据库”还不能直接执行。“自己写一条筛选查询，说明每个条件，保存结果和解释”才足够具体。一个大项目中的小任务完成后，大项目通常仍在推进中。

## 3. 建立独立对话，留下交接

创建前先检查现有对话，合适的继续使用。新对话的首条消息写明目标、资料位置、已有结果、下一步和操作边界。仅创建入口时，让它读完交接后等待，避免所有长期任务同时启动。

总览负责时间冲突、优先级和新的事实；任务对话负责本任务的实际工作。每个任务对话完成一次有结果的动作后，只更新自己的那一行。不要让它顺手改掉其他任务的进展或全局安排。

创建新对话和向已有对话发送消息要得到用户授权。独立对话是用户以后会直接打开的持续入口；当前请求内的临时研究或实现分工则是子 agent，二者用途不同。本方法不要求开启子 agent。

## 4. 总览只有一个事实来源

最小版本用 `private/tasks.md`。由总览写入，任务对话给出回传内容；需要多对话直接更新时，再使用支持版本检查和历史记录的存储。多个对话各存一份完整清单，容易出现互相覆盖和过期副本。

写入前读取最新内容；合并自己负责的字段，不覆盖整张表。更新冲突时先比较双方变化，再提交。数据库应使用事务和版本号，保留更新时间与历史；Markdown 也需要串行写入或差异合并。

“实时”的最低含义是：记录更新后，展示端能读到新记录。它不等于 AI 自动监听所有软件，也不等于学习过程自动评分。如果目前还需要手动回传，就明确写出这个步骤。

## 5. 用本人结果更新进展

| 看到的东西 | 能说明什么 | 还需核对什么 |
| --- | --- | --- |
| 播放课程、打开编辑器、角色坐到书桌旁 | 一项活动发生或被声明 | 是否理解、是否有可检验产物 |
| AI 生成了解答或代码 | 有候选产物 | 本人是否能重做、解释；代码能否运行 |
| 本人独立做题、代码运行结果、实际回执 | 支持相应的结果 | 适用范围、提示程度、后续复测 |

带提示完成、独立完成、只阅读过，要分别记录。进展可以是“找到了卡点并完成一小段练习”，不必每天伪装成大突破。没做成时先辨认：下一步太大、前置知识不够、资料不足、时间冲突，还是不想继续。不要仅凭一次停滞给人贴“执行力不足”的标签。

## 6. 把入口接回实际使用的产品

Career Workbench 的小屋子是日常入口：收起时尽量少打扰；小窗展示当前行动；展开后查看完整清单、进展依据和任务对话。新增清单应接入既有房间，而不能因为另做一张页面更方便，就把用户熟悉的入口替换掉。

房间、总览和任务对话读取同一事实来源。角色动作可以表达明确开始的行动，不能充当学习完成或目标达成的证据。界面验收要实际测试收起、展开、更新、重开和恢复，并区分浏览器预览与原生窗口验证。

小屋子与相关集成目前分散在草稿分支中；仓库 `main` 的能力以根目录 README 为准。这份指南不把讨论、截图或草稿 PR 当作完整产品已交付。

## 今天就可以做的最小版本

1. 用收集提示词，整理一份不超过当前注意力范围的任务清单。
2. 选一件今天的重点，写明输入、产物和验收。
3. 给确实需要持续推进的方向建立独立对话，交接后等待。
4. 做一次小行动，把实际结果回传到同一份清单。
5. 根据卡点修改下一步；需要改变安排时先把新的安排展示给本人。

每天可以人工复盘。提醒、定时检查和活动监测是另外的设置，需要指定数据来源、频率、触发条件和退出方式；复制提示词不会自动启动这些能力。

## 怎么分享给同学

分享本指南、空任务卡、提示词和虚构示例。每位同学在自己的 `private/` 中填写约束和记录，自己指定允许读取的资料。公开演进记录保留通用问题、决策、证据和限制；私人笔记、真实聊天、真实任务数据库、简历、账户信息和截图留在本机。

同学试用时优先反馈：能否找到正在做的任务、能否说清下一步、进展记录是否与本人实际结果一致。之后再比较工具是否减少了重复整理和上下文切换；这些效果需要实际使用证据。
